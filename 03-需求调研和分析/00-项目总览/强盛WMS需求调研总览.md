## 三、统一记录与确认方法

模块调研稿依次交代范围与来源、沙盘角色、场景与问题、诉求和待核实边界；模块分析稿交代结论、诉求处理、追溯、功能、依赖、拟定验收和待决策。篇幅随模块复杂度调整，不为凑章节重复内容。

采用“模块前缀-类型-三位序号”，例如IN-S-001、IN-P-001、IN-R-001、IN-BR-001、IN-FR-001、IN-AC-001。S、P用于有来源的场景和问题，R用于原始诉求；BR、FR、AC分别用于业务需求、功能需求与验收。原始诉求在调研稿第四节按行编号，分析稿逐条引用同一编号并写明采纳、不采纳或后置的理由。

追溯分两条路径：

- 有依据的现状或明确标注的沙盘场景 → S／P → BR → FR → AC。
- 已确认的目标决定 → BR／FR → AC；注明来源文件及小节，不为填满矩阵编造S／P。

每条已采纳的系统类BR至少对应一个FR，每个FR至少对应一个AC；不采纳或后置的诉求保留处理理由，不伪造一期FR。编号删除后不复用；新增、调整或删除功能时，同时更新处理表、追溯矩阵、功能需求和验收。跨模块引用须写完整编号及文件位置。

| 记录维度 | 使用状态 | 说明 |
| --- | --- | --- |
| 来源性质 | 现状证据／沙盘设定／沙盘推演／目标确认／竞品参考／原型参考 | 性质不能互相替代 |
| 证据核实 | 待补资料／待核实／已核实 | “已核实”只针对明确来源中的具体事实，不代表生产验证 |
| 目标结论 | 待分析／待决策／已确认／后置／不采纳 | 只有已有确认依据的结论标为已确认；未决建议直接归入待决策 |

总览的项目级结论引用全局背景；形成模块需求后，模块摘要须能定位到模块编号。已确认事项移出待确认表，剩余细节单独记录。未指定确认人或日期时如实标注，不编造负责人；最迟时点可用“对应模块设计前”等阶段门槛表达。
