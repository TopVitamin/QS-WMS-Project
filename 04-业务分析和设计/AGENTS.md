# 强盛WMS业务分析和设计：写作约定

全项目文档编号与简码通则见[根目录 AGENTS.md](../AGENTS.md)。

本目录承接已确认的项目背景与需求，说明业务由谁、在什么条件下执行，产生什么结果，下一步交给谁。当前8份正文（含退货业务设计）已补齐，可供业务走查和后续应用设计使用；真正未决的问题保留在负责正文及蓝图汇总中，文档检查不表示业务验收已经完成。

## 业务设计写什么、不写什么

本目录的「业务设计」服务于**强盛一期海外仓 WMS 执行链**（资料→入库→库存→出库→上游协作），写法上**偏运行与后果**，不重复立法、也不提前做产品稿。

### 与 03、05 的分工（读一层、写一层）

| 层级 | 目录 | 本目录与其关系 |
| --- | --- | --- |
| 需求 | `03-需求调研和分析` | **调研**记诉求与缺口；**分析**维护功能真源（各模块第二节 FR）。业务设计**展开**已确认规则，不推翻、不替代分析第二节。 |
| 业务设计 | `04-业务分析和设计`（本篇） | 场景、责任、流程、对象关系、数量／资格走查、异常与跨域交接。 |
| 应用设计 | `05-应用设计方案` | 字段、状态枚举、页面、权限点、消息形态；**不得反向创造**会改变数量、责任或准入的业务规则。 |

正文里优先用**中文模块名**写清归属；只在需要跳转真源或竞品原文时再加链接。与 [03 目录 AGENTS](../03-需求调研和分析/AGENTS.md) 配套阅读。

**链接克制（默认）**

| 保留链接 | 尽量少链或不链 |
| --- | --- |
| §一 指向本域《需求分析》一次（真源） | 文首重复链同一分析稿；文内锚点到 §1.2 等小节 |
| 竞品高频表里的原文页（证据） | 同目录 02～05 业务设计互链（写「入库域」「出库域」即可） |
| 06 综合场景、蓝图（索引入口，每篇至多一处） | §一 堆链各模块分析稿 + 调研 + 定位 + 双边矩阵 |
| 长文内走查索引表 → 本章锚点（给人翻页） | 正文段落里链到 03 FR 锚点、链到邻域具体节号 |
| 应用权限、COM 等 05/07 边界（每域一处） | 同一规则在摘要段、异常表、§十 重复链基础资料 |

FR 编号集中在 §一 依据或单条括号引用，不在段落中成串粘贴。

### 偏向什么

- **执行视角**：谁在什么条件下做什么，实物／0量落在哪，结果交给谁或哪个域继续处理。
- **判断与后果**：条件不满足时阻断什么、保留什么、如何恢复；区分「拒收指令」与「作业节点失败」等不同失败类型。
- **海外仓共性**：多货主同仓、四仓分别记账、货主＋SKU（及批次／SN）追溯、上游指令与仓内结果可区分。
- **可走查**：用时间序案例验规则（数量走查、资格链走查）；复杂综合场景在 [06](06-海外仓典型业务场景与方案.md) 引用各域锚点，不另换一套数字。
- **诚实边界**：课程沙盘与竞品原文作依据；岗位未访谈的写「未指定」；演示样例可标注性质，不冒充现场制度。

### 不偏向什么

- **ERP 全套业务设计**：采购／销售订单分层、业财结算、定价、逻辑仓、在途账、供应商客户主数据审批流等一期 WMS 范围外模型（见蓝图与项目定位）。
- **需求调研体例**：现状访谈复述、诉求表再抄一遍 FR、场景号／问题号编码（`MD-Sxx` 等）、整页 FR 追溯矩阵。
- **应用与实现体例**：页面跳转、按钮名称、表单布局、接口路径、库表、索引、设备选型、并发与性能方案。
- **把竞品能力直接写成一期步骤**：竞品只作能力与证据索引；候选方案进 06 §8.2，各域只留入口。

### 重点关注什么

- **交接唯一**：上游给什么、本域交出什么、交给谁（文首或 §二 宜用交接表）；跨域数量口径以库存与库内需求及本目录 04 域为准，入库／出库引用不重定义。
- **量与占用分清**：实际库存、入库过程量、订单预占、品质锁定、已确认出库待交接、盘点冻结等，写清**不能混算**的场景。
- **对象关系**：基数、可选性、从单据／任务追到货主、位置、追溯身份的路径。
- **变更分治**：改名、配置开关、停用等不同变更类型，分别写影响检查（不要一句「有单就不允许」盖掉）。
- **异常闭环**：触发、业务后果、责任方、能否恢复；与 §流程／§规则分工一致，避免同一结论在多处措辞漂移。
- **权威同步**：业务设计新增或收紧且影响验收的结论，应回写对应 **03 分析稿**；应用设计只落实，不在 PRD 里单独「定法」。

### 不关注什么

- 字段级定义、控件校验文案、状态机枚举完整表（见 05 字段清单与 [03-单据与状态流转](../05-应用设计方案/20261002-MVP版本/系统架构设计/03-单据与状态流转.md)）。
- 菜单是否合并、列表默认排序、页大小、编码前缀等产品细节（除非 03 已确认为业务规则）。
- 测试通过记录、原型验收、接口联调结果；交付检查只说明**文档与走查**范围，不声称生产验证。
- 把「待补演示样例」写成已确认仓库制度；样例缺口记在 §九 或调研总览，与已确认规则分开。

## 资料分层与权威来源

- 01-全局背景信息维护公司背景、项目定位、范围、系统分工和阶段边界。
- 02-竞品调研和分析提供行业与竞品依据。先读竞品取舍和原文索引定位，再回到对应原始操作页；二次知识库仅作导航。仅标题或未核验截图不能支持规则结论。
- 03-需求调研和分析维护目标需求、已确认规则及关键规则；[分析总览](../03-需求调研和分析/00-项目总览/02-需求分析总览.md)用于定位当前结论和未决问题。
- 04-业务分析和设计展开目标业务的场景、责任、流程、对象关系、数量变化及异常后果，不自行覆盖上游已确认规则。
- 05-应用设计方案承接字段、单据分层、系统状态枚举、页面交互、权限配置、接口协议和技术机制；09-产品原型展示实现，不能反向创造业务规则。业务蓝图阅读顺序中的「05」指本目录 `05-上游协作与结果交接设计.md`，不是应用设计下的 `05-全局机制与权限配置.md`。
- 发现矛盾先定位当前文件与确认依据；不能判定时列明影响和待决策点。公司与量级是课程沙盘，竞品操作是产品能力证据，不冒充真实企业访谈或运行记录。

## 正文维护的深度与范围

- 文首一句 disclaimer +「顺读从 §二 起」；§一 放依据与竞品**索引**（链 03 与 §九），不堆 FR 长表。开头写清本域处理什么、与谁交接；现有大纲可按实际材料裁剪，不为章节齐全填空话。
- 场景写触发、参与方、关键判断、结果与后续环节；流程写谁做什么、实物在哪里、结果交给谁，不重复抄同一段规则。
- 对象关系说明基数、可选性和追溯路径；有数量流动的域写清量落在哪个对象、如何累计、扣减和释放，并用明确标注的模拟数字走查。
- 异常说明触发、业务后果、责任和恢复方式；未指定岗位标明待明确，不自行新增审批或责任层级。
- 新方案分为已确认、待细化、候选和后续阶段；竞品功能不能直接变为一期步骤。资料缺口与业务待决策分别写，已确认事项不反复列为未决。
- 跨域数量定义以库存与库内需求分析为依据，由本目录 04 域展开运行解释；入库、出库域引用。变更取消的执行节点由 02／03 入库、出库设计展开，05 只说明交接；06 引用域内规则。
- 每套数量案例在负责域维护完整输入、时间线与结果，综合场景引用该案例，不另换数字冒充同一时间线。各域 **§八（及出库 §九）** 先放**案例索引表**（场景一句、结论一句、锚点），详表留在单点小节；库存域分散在 §七、§八 的模拟用 §9.0 汇总跳转。候选的价值、证据与采用条件集中维护在06第8.2节，各域只保留入口；跨域竞品原文以 06 文末引用为全集，各域 §一或竞品表只留本域高频。蓝图 §6.1 串联公共能力走查，不单建 COM 正文。蓝图汇总当前未决事项，不重复历史确认清单。
- 默认只读本地已留存资料；需要声称当前官方能力或补外部事实时再核验一手来源，说明核验日期与范围。无需为每份文档重查全部竞品。
- 系统状态、字段、接口、算法实现和设备选型交给应用设计；业务阶段与后果必须在本层讲清，不用“后续设计”掩盖会改变数量或责任的未决分叉。

## 子任务协作

- 按用户或父任务指定文件补正文，跨文件修改仅在明确分工范围内进行；先回读当前文件和上游资料，保留其他Agent及用户的改动。
- 当前8份正文按目标业务维护；文首不再使用骨架或待补阶段的完成说明。未决规则与资料缺口分别记录，候选不表示已批准。
- 对共享规则的新判断或冲突，报告依据、影响和关联文件，不直接改写其他子任务文件。蓝图与06最终依据各域结论收口。
- 不因本约定自行启动Agent、创建新聊天或给其他聊天发消息；由当前任务授权决定分工。

## 交付检查

1. 范围与当前背景／需求一致，海外仓场景有项目理由和可定位的竞品依据；不照搬ERP价格、业财、逻辑仓或跨仓在途模型。
2. 角色与交接完整，实际结果、作业进度、库存、品质、效期和占用关系分清，数量走查不重不漏。
3. 资料与规则引用有效，跨域条件一致，候选与后续阶段明确；待确认只保留真正未决问题。
4. 规则变化后检查蓝图索引、案例、候选边界与相关引用；已解决事项移出未决清单，未解决项保留，并与需求分析总览一致。
5. 文档结构与链接检查不等于演示、接口、并发或生产验证，交付如实说明实际检查范围。
